## Chat coupling and minimal desktop seam (recommendation only)

**Verified coupling:** `mobile/lib/app/app.dart` creates `ChatRepository` and injects it into `SyncCoordinator`; `OrialisApp.initState` starts that coordinator. `SyncCoordinator._onEvent` applies every `message` realtime envelope to chat storage. `SyncEngine.syncOnce()` calls conversation pushes, conversation pulls, message pushes and message pulls, and the HTTP API client has conversation/message/attachment endpoints. `AppDatabase` owns `conversations` and `messages`, plus a chat-only query. These are real pathways, so hiding `/chat` alone would not isolate a desktop client.

**Smallest seam to evaluate with the mobile/sync owner:**

1. Inject a typed client capability policy/handler into `SyncEngine` (for example, domain-only vs domain+chat). Guard every conversation/message/attachment push and pull at the engine boundary. A domain-only sync pass must make zero chat HTTP calls and zero chat-table reads/writes; keep chat schema/tables/migrations intact for compatibility.
2. Give `SyncCoordinator` an optional realtime message handler (`null`/no-op for domain-only) separate from its common sync-trigger handler. Continue to handle `hello.ack`, `sync.change_hint`, `change_hint`, and `change.hint` as triggers, while leaving ping/pong and reconnect transport active.
3. Retain one domain sync pipeline for task, schedule, project, milestone and outbox mutations. Preserve snapshot bootstrap, cursor page validation/transaction coupling, tombstones, 409 local-write retention, HTTP fallback/recovery and resume-triggered sync. Unsupported message/agent envelope types must be ignored safely without writing chat state and without altering domain cursor semantics.
4. Desktop realtime hello should report an actual platform/client identity and only relevant capability names; current client sends `platform: android` plus chat/agent capabilities. Whether server-side capability negotiation depends on those names is unverified and needs protocol/server-owner review.

This is a **proposal for an injection boundary**, not a confirmed design. Owning roles: the `mobile/**` path owner/coder for app/providers, database and API client; the sync/realtime path owner/coder for `mobile/lib/core/sync/**` and `mobile/lib/core/realtime/**`; desktop coder for the new Runner and desktop entry; architect decides cross-boundary contract. Determine exact Role assignees from the project board before implementation. This report neither grants cross-owner write access nor accepts the current dirty tree as a baseline.

## Identity and server isolation risks

| Verified mechanism | Risk / unknown (not asserted as a proven data leak) | Required check and owner |
| --- | --- | --- |
| `AppDatabase` always opens `driftDatabase(name: 'orialis')`; all current task/project/schedule rows and the single `serverCursor`/snapshot metadata key share that DB. | `AppConfig.setServerUrl()` changes one global preference without namespacing or resetting local rows/cursor. A server switch may send prior local domain data/cursor to the newly configured server, or cause cursor/snapshot mismatch. Exact server behavior not tested. | Define server/account partition key or explicit switching flow with export/retain semantics; test switch A→B with pending rows and nonzero cursor. Owner: mobile/database + sync coder, architect approval. |
| One persisted preference `orialis.deviceId`, session token in secure storage, username preference; sign-out clears credentials, not the database or device ID. | Device ID is not account/server scoped. A new login/server can reuse the prior ID while sharing local data/outbox. Whether backend treats it as stable app-install identity is undocumented here. | Confirm server device identity semantics; test logout/login account switch, expired session, and server switch. Define whether to retain, partition, or explicitly clear data. Owner: auth/API + infrastructure owners. |
| Outbox rows and mutation IDs are in the same database, and `SyncEngine._readCursor()` uses global key `serverCursor`. | Pending outbox writes might cross account/server boundaries if the endpoint/session changes before they drain; domain cursor could be inappropriate for a different server. This is an inferred risk from the shared store. | Gate sync on a stable `(server origin, account identity)` binding and specify safe transition/recovery. Do not clear/overwrite existing user changes without review. Owner: sync/database owner and architect. |
