## 最终行为

普通用户消息开始时，插件创建独立的 `TurnUpdates`。首回应模型在后台生成，Hermes 主处理立即继续，不等待首回应生成或送达确认。若正文、原生中间消息或实际回复先输出，取消尚未发出的首回应，直接发送实际内容；home-channel 设置提示、旧版空“✅”与非对话通知不会抢掉自然首回应。不为保证先出现一句开场白而等待。此前非思考辅助模型、12 秒调用预算、稳定首回应缓存和 `initial_` ID 继续沿用，没有调整四台主模型、供应商或正文 low 配置。

中途汇报分两路。Hermes 原生 `Commentary` 是主模型在工具迭代间已经生成的公开中间消息，继续按现有消息链路投递；`PLATFORM_HINT` 鼓励有实际阶段变化时自然说明已确认进展及下一步，短任务无需额外开场或重复状态。另一条本地补充任务在长时间没有公开输出时约每 30 秒检查真实阶段，按当前状态生成简短句子。它不调用辅助模型，不增加进度 LLM 请求。

本地状态只取实际收到的“处理中”“工具调用中”“工具调用已返回”，并根据公开工具名称归为查找资料、查看文件、执行任务步骤等类别。不会查看工具参数、原始结果或隐藏思考，不把工具返回等同工具成功，不虚构调查结论或验收结果。`Commentary` 的措辞由主模型结合其已有上下文自然生成；本地补充状态属于事实短句，不是另一轮模型分析。

新增后台首回应和本地补充进度不进入主处理的等待链：独立任务负责发送和等待 ACK，主回复不等待它。原生 Commentary 沿用 Hermes 既有投递机制，本次未修改其内部发送队列。没有阶段变化时不重复汇报；多次快速变化只保留最新阶段，避免逐条工具日志刷屏。`progress_` ID 由本轮用户 anchor 与汇报文本确定，重复投递同一句不会产生新的消息身份。进度关联原用户消息，不发 `agent.complete`。

主文本输出时取消待发进度并暂停补充汇报，新工具阶段才可恢复。完成、停止、断线以及同会话新任务开始时关闭旧轮更新，取消未完成首回应和进度任务。跨线程状态回调回到网关事件循环执行，旧轮状态不能改写新轮。TASK-019 已有冷启动队列身份检查保留，启动暂存不提前完成。

## 性能边界

这次移除了串行等待首回应的环节；主回复不等待首回应模型、初始 ACK 或进度 ACK。本地进度不新增模型请求，因此不与主模型争用额外的进度推理容量。原有首回应仍会发起辅助请求；服务端、网络或上游共享容量的耗时仍由实际运行决定，不能将“不增加串行等待”写成绝对零开销保证。实测长任务特意运行 42 秒等待命令，耗时包含模型、工具和基础设施等待，不能用作性能增减的统计对照。Windows 快任务 3.388 秒直接发完整回复，首回应与中途进度都未抢先或迟到。
